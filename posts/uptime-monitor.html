Why I built it

I wanted to learn Go, and specifically its concurrency: goroutines, channels and worker pools on something real rather than tutorial examples. An uptime monitor was a natural fit, and it is something I can actually use to watch my own deployed projects, like the billing API.

The failure

A monitor checks many endpoints. If checks run one after another, a single endpoint that hangs makes every check behind it late, so healthy sites look slow or go unchecked.

How it's guarded

  • A scheduler asks PostgreSQL every 5 seconds which monitors are due and dispatches them to a goroutine worker pool over a buffered channel.
  • In-flight probes are tracked so none is queued twice.
  • Each probe is stored as a row, writing the check and the monitor's last-checked time in one SQL statement.
  • Graceful shutdown saves every in-flight result before the database pool closes.
$ go test -race ./...
hung + healthy endpoints   workers: pool   PASS
hung + healthy endpoints   workers: 1      FAIL  # test catches it

What I learned

The bug that got me first: the scheduler sometimes dispatched a monitor that was still being checked, so the same probe ran twice. The fix was tracking in-flight probes and skipping any monitor that is already running.

  • Go makes concurrency explicit. Compared to Node's event loop or Celery workers, you decide exactly how many things run and how they talk.
  • Bound everything. A fixed pool size and a buffered channel stop one slow endpoint from taking over.
  • Shutdown is a feature. Stopping cleanly, without losing in-flight results, matters as much as running.
