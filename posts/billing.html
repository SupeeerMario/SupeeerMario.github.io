Why I built it

I read about a real race condition where two requests hit the same invoice at once and the customer got charged twice. I wanted to understand how that happens and how to make it impossible, not just unlikely.

It was also my excuse to go deeper with Django REST Framework (custom authentication, API design) and Celery with Redis for scheduled jobs like monthly invoicing.

The failure

Two payment requests for the same invoice arrive at the same moment. Both check "is this already paid?", both see "no", and the customer gets charged twice. A check in Python can't stop this, because both requests pass it before either one writes.

How it's guarded

  • A unique index on (tenant, idempotency key) makes PostgreSQL reject the second payment, no matter how close together they arrive.
  • Every money movement goes into an append-only double-entry ledger. Tests assert it sums to zero and that receivables equal open invoices, before and after payment.
  • A custom DRF API-key auth class scopes every query to one tenant.
  • Monthly invoicing runs on Celery beat, with unique constraints so no run bills twice.

What I learned

My first fix was a Python check: "if the invoice is already paid, stop." It looked right and passed a normal test. The concurrent test fired 8 payments at once and recorded 8 charges, because every request passed the check before any of them wrote. Moving the rule into a unique index in PostgreSQL is what fixed it.

The double-entry ledger took me longest. Getting debits and credits to always sum to zero made me slow down and think about where money actually moves.

  • Let the database enforce rules. Under concurrency, constraints beat application checks.
  • A test only counts if it fails without the guard. Removing the index and watching the test go red is the real proof.
  • Money needs a ledger. Never just update a balance; record every movement.
  • Tenant isolation breaks easily. One unscoped query and customers see each other's data, so scoping lives in the auth class, not in each view.
