Why I built it

Almost every company imports spreadsheets, and most importers quietly break on big files. After the OCR freelance job taught me that heavy work has to leave the request path, I wanted to push that idea further: what actually goes wrong at 500,000 rows, and how do you survive a worker dying halfway?

The failure

A user uploads a huge CSV. Halfway through, the worker processing it crashes. Without a record of where it stopped, a restart either skips rows or imports some of them twice.

How it's guarded

  • Uploads stream straight to S3-compatible storage (MinIO) and return HTTP 202 with a job ID, so the request never waits on parsing.
  • Each 1,000-row chunk and its checkpoint commit in one MongoDB transaction: either both are saved or neither is.
  • Redis Streams consumer groups give at-least-once processing; idempotent upserts make a repeated chunk harmless.
  • Transient failures retry; after 5 attempts a message goes to a dead-letter stream, and rejected rows come back as a streamed CSV report.
$ import 500,000 rows (30 MB)   memory: 120-131 MB flat
$ kill worker-1                  # mid-import
$ start worker-2                 # resumes from checkpoint

What I learned

Redis Streams was the hardest part. Consumer groups, acknowledging messages, and what happens to pending messages when a consumer dies all took a while to click. Getting retries and the dead-letter stream right depended on understanding that first.

  • Return 202, work later. The user gets a job ID right away; the heavy work happens in the background.
  • Stream, don't load. Processing the file in chunks keeps memory flat no matter how big the upload is.
  • Crashes are normal. Design for the worker dying, with checkpoints saved in the same transaction as the data.
